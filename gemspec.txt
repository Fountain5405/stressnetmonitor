Monero StressNet Telemetry and Analysis System: A Comprehensive Specification1. Executive Summary and Theoretical UnderpinningsThe scalability of privacy-centric distributed ledgers represents one of the most significant engineering challenges in the modern cryptocurrency landscape. Monero (XMR), utilizing the CryptoNote protocol and subsequently the RandomX proof-of-work algorithm alongside RingCT (Ring Confidential Transactions) and Bulletproofs, presents a unique set of computational constraints distinct from transparent ledgers like Bitcoin. While transparent blockchains primarily face bandwidth and storage bottlenecks, Monero’s privacy features impose a heavy computational verification tax on every node participating in the network. This verification burden includes the validation of range proofs to ensure non-negative transaction amounts without revealing the amounts themselves, and the checking of key images against a local state to prevent double-spending without revealing the spender's identity.As the Monero network grows, or as block size limits are experimentally increased in a "StressNet" environment, the resource requirements for maintaining synchronization with the network tip scale accordingly. The user's objective—to empirically determine the "breaking point" at which legacy hardware fails to keep up with large blocks—addresses a fundamental question of decentralization: at what point does the hardware requirement for running a node become exclusionary, effectively centralizing the network into the hands of data center-grade operators?To answer this question rigorously, a "feeling" or anecdotal observation of node sluggishness is insufficient. What is required is a Monero StressNet Monitor (MSNM), a distributed telemetry and analysis system capable of quantifying "incapability." This system must operate on a Hub-and-Spoke architecture, utilizing a high-performance Reference Node to establish the "ground truth" of the blockchain state (the Hub) and a fleet of asynchronous scraper agents to poll test nodes (the Spokes).This report serves as a comprehensive functional and technical specification for the MSNM software. It details the architectural topology, data acquisition strategies via the monerod JSON-RPC interface, failure mode definitions (distinguishing between I/O saturation, CPU verification lag, and memory exhaustion), and the analytical methodologies required to process the resulting time-series data. The specification is designed to be handed to a Coding Agent for immediate implementation, ensuring that the resulting software is robust, fault-tolerant, and capable of generating the high-resolution data needed to plot the hardware capability curve against block size growth.1.1 The Mechanics of Monero Verification LoadUnderstanding the monitoring requirements necessitates a deep understanding of what the monitoring software is actually observing. When monerod receives a block, it does not merely append it to a file. It performs a rigorous series of cryptographic checks. The block verification time ($T_{verify}$) is a function of the number of transactions ($N_{tx}$), the complexity of the range proofs, and the state of the local database (LMDB).$$ T_{verify} \approx T_{header} + \sum_{i=1}^{N_{tx}} (T_{ring_sig} + T_{range_proof} + T_{key_image_check}) $$In a StressNet scenario where block sizes are artificially inflated, the $N_{tx}$ term dominates.CPU Saturation: RandomX and Bulletproof verification are CPU-intensive. If $T_{verify}$ exceeds the block target time (nominally 2 minutes for Monero), the node will fall behind, creating a "Sync Lag" that grows linearly over time.I/O Latency: Monero uses LMDB (Lightning Memory-Mapped Database), which relies heavily on the operating system's page cache. As the blockchain grows, or as the "working set" of unspent outputs accessed by large blocks exceeds available RAM, the system begins to "thrash." The disk I/O required to check key images against the database becomes the bottleneck. This is particularly devastating for spinning Hard Disk Drives (HDDs), where random read performance is poor.Memory Pressure: While Monero is optimized, handling blocks in the tens or hundreds of megabytes requires significant RAM buffers for serialization and deserialization. On legacy hardware with 4GB or less RAM, this pressure can trigger the Linux Out-Of-Memory (OOM) killer, resulting in the sudden termination of the monerod process.The monitoring software must be sensitive enough to distinguish between these failure modes. A node that is lagging due to CPU saturation looks different in telemetry (high CPU usage, slow but steady progress) than a node lagging due to I/O saturation (low CPU usage, high I/O wait, RPC timeouts).2. System Architecture and Network TopologyThe proposed solution eschews a decentralized gossip-based monitoring approach in favor of a centralized, authoritative polling model. This is necessary because the "Old Computers" (Test Nodes) are the subjects of the experiment and are expected to fail. Relying on them to push data reliably is a flaw in experimental design; a frozen node cannot push logs. Therefore, the architecture relies on an external observer actively probing the subjects.2.1 The Hub-and-Spoke ModelThe system consists of three distinct physical or logical layers:The Reference Layer (The Hub):Component: Reference Node ($N_{ref}$).Hardware: Modern, high-specification server (e.g., NVMe storage, high-frequency CPU, 32GB+ RAM).Role: Defines the "Canonical Chain." In a StressNet, where forks and reorgs are likely due to network instability, $N_{ref}$ serves as the arbiter of truth. If a Test Node is at height $H$ but has a different block hash than $N_{ref}$ at height $H$, the Test Node is considered to have forked.Software: Standard monerod instance, configured for maximum stability.The Monitoring Layer (The Observer):Component: Monero StressNet Monitor (MSNM).Location: Co-located with the Reference Node or on a machine with low-latency LAN access to it.Role: The central orchestration engine. It maintains the registry of Test Nodes, schedules polling cycles, computes derived metrics (lag, fork depth), and persists data to the Time Series Database (TSDB).The Test Layer (The Spokes):Component: Test Fleet ($N_{test\_1}... N_{test\_n}$).Hardware: The heterogeneous collection of "old computers" provided by the user.Role: Passive subjects. They run monerod with open RPC ports. They do not run complex monitoring agents to minimize the "observer effect" (stealing CPU cycles from the daemon). A lightweight system-level scraper (optional sidecar) may be used for OS metrics.2.2 Network Communication SpecificationsThe MSNM interacts with the nodes primarily via JSON-RPC over HTTP. This requires specific network configurations on the Test Fleet to allow the MSNM to connect.Protocol: HTTP (or HTTPS if configured with stunnel/nginx, though HTTP is standard for private LAN stress tests).Ports: The default Mainnet RPC port is 18081. For a private StressNet, custom ports (e.g., 38081 or 48081) are often used to avoid conflict.Binding: By default, monerod binds to 127.0.0.1. Test nodes must be launched with --rpc-bind-ip 0.0.0.0 and --confirm-external-bind to listen on all interfaces, allowing the MSNM to poll them.Security Context: In a controlled "Private Stress Net," strict firewalling at the network edge is assumed. However, if the network is shared, the software specification includes support for --rpc-login (Digest Authentication) to prevent unauthorized control of the nodes.2.3 Data Flow DiagramThe flow of information during a single polling interval ($t$) is as follows:Initialization: MSNM loads nodes_config.json.Baseline Acquisition: MSNM queries $N_{ref}$ for get_info and get_last_block_header. This establishes $H_{target}$ (Target Height) and $Hash_{tip}$ (Tip Hash).Concurrent Polling: MSNM spawns asynchronous workers to query every $N_{test}$ in parallel.State Comparison:Worker $i$ retrieves $H_{test\_i}$ and $Hash_{test\_i}$ from Node $i$.Worker $i$ calculates $Lag_i = H_{target} - H_{test\_i}$.Worker $i$ checks Fork Status: If $H_{test\_i} \approx H_{target}$ but $Hash_{test\_i} \neq Hash_{tip}$, a fork event is flagged.Latency Tracking: Worker $i$ measures the round-trip time (RTT) of the RPC request ($t_{end} - t_{start}$).Ingestion: Metrics are written to the TSDB (e.g., InfluxDB).Alerting: If $Lag_i$ exceeds a critical threshold, an alert is generated (log/console).3. Reference Node Specification: Establishing Ground TruthThe validity of the entire experiment rests on the Reference Node. If the Reference Node falls behind, the "lag" calculations for the Test Nodes become meaningless. Therefore, the specification requires the Reference Node to be over-provisioned.3.1 Hardware RequirementsBased on Monero performance benchmarks and the nature of "Stress Testing" (where blocks might exceed 10MB or 100MB), the Reference Node must eliminate I/O and CPU bottlenecks.Storage: NVMe SSD is mandatory. SATA SSDs may become a bottleneck at extreme block sizes. The monerod data directory must be on this volume.RAM: 32GB minimum. This allows the OS to cache a significant portion of the LMDB file, reducing read latency.CPU: High single-core clock speed (e.g., Ryzen 9 or Intel i9) is prioritized over core count, although monerod does utilize multi-threading for block verification.3.2 Daemon Configuration for ReferenceThe Reference Node should run with specific flags to ensure it processes blocks as fast as possible and provides robust RPC service:--db-sync-mode fast: potentially risky for crash consistency but maximizes write speed during the test.--rpc-payment-allow-free-loopback: Ensures the MSNM (if local) isn't rate-limited or charged credits.--out-peers 64: Maintains a high degree of connectivity to the StressNet to ensure rapid block propagation reception.--no-igd: Disables UPnP to reduce overhead, assuming static networking.4. Telemetry Acquisition: The RPC Interface SpecificationThe core of the MSNM is the Poller module. This module interprets the monerod RPC interface. The following section specifies exactly which endpoints must be queried, the fields to extract, and the derivative metrics to calculate. This serves as the blueprint for the Coding Agent's API client.4.1 Global Node Status: get_infoThis is the "heartbeat" endpoint. It is lightweight and provides the primary synchronization metrics.Endpoint: /json_rpc -> get_infoCritical Fields to Extract:height (unsigned int): The number of blocks in the node's local longest chain.target_height (unsigned int): The height the node wants to reach (based on advertisements from peers).difficulty (unsigned int): Network difficulty. Used to verify the node is on the correct StressNet and not accidentally on Testnet/Mainnet.cumulative_difficulty (unsigned int): Crucial. This is the mathematical definition of the "longest chain." If a Test Node has the same height as the Reference Node but lower cumulative_difficulty, it is on a minority fork.tx_pool_size (unsigned int): The number of transactions in the mempool. In a stress test, a lagging node might drop transactions or fail to verify them, leading to a diverging pool size.database_size (unsigned int): Monitoring the growth of the LMDB file. This allows correlation between "Disk Full" events and node failure.busy_syncing (boolean): Explicit flag indicating if the node considers itself to be in synchronization mode.status (string): Should be "OK". Any other value indicates internal daemon error.Derived Metrics:Sync Lag: $Lag = H_{ref} - H_{test}$.Sync Health: If busy_syncing is TRUE but height has not changed for $N$ poll intervals, the node is "Stuck."4.2 Chain Consistency Verification: get_block_header_by_heightTo detect "Silent Forks" or "Reorgs" (where a node is synced but to the wrong chain), the MSNM must perform a hash check.Endpoint: /json_rpc -> get_block_header_by_heightParameters: {"height": <CURRENT_TEST_NODE_HEIGHT>}Critical Fields to Extract:hash (string): The block hash.prev_hash (string): The parent block hash.timestamp (unsigned int): Block creation time.num_txes (unsigned int): Transaction count.block_weight (unsigned int): The size of the block. This is vital for correlating failure with specific block sizes.Analysis Logic:The MSNM queries the Test Node for the header at its current tip $H_{test}$.The MSNM checks its internal cache (populated by the Reference Node) for the hash at height $H_{test}$.Comparison:If $Hash_{test} == Hash_{ref}$: Node is Synced and Valid.If $Hash_{test} \neq Hash_{ref}$: Node is Forked.Reorg Depth Calculation: If forked, the MSNM should walk backward (querying $H_{test}-1, H_{test}-2...$) until the hashes match. The distance is the Reorg Depth. High reorg depth on specific hardware indicates it is losing the propagation race or rejecting valid blocks.4.3 Network Health and Partitioning: get_connectionsA node might be "online" (responding to RPC) but disconnected from the P2P network, essentially dead to the world.Endpoint: /json_rpc -> get_connectionsCritical Fields to Extract:List of connections:address (string): Peer IP.state (string): e.g., "state_normal", "state_synchronizing".avg_download / avg_upload (unsigned int): Bandwidth utilization.recv_count / send_count: Total data transferred.incoming_connections_count vs outgoing_connections_count.Analysis Logic:Isolation Detection: If outgoing_connections_count drops to 0, the node is isolated.Bandwidth Saturation: During large block phases, monitor current_download. If this caps at the hardware's NIC limit (e.g., 10MB/s on a 100Mbps card) while lag increases, the bottleneck is Network Bandwidth, not CPU/Disk.4.4 Transaction Pool Analysis: get_transaction_pool_statsBlock propagation is only half the battle; transaction propagation is the other. The "Fluff and Flood" mechanism (Dandelion++) relies on nodes relaying transactions.Endpoint: /get_transaction_pool_stats (Binary/Non-JSON endpoint usually, or /json_rpc -> get_transaction_pool_stats depending on version).Critical Fields:bytes_total (unsigned int): Total size of mempool.txs_total (unsigned int): Number of transactions.oldest (unsigned int): Timestamp of the oldest tx.Analysis Logic:Mempool Divergence: If $Mempool_{test} \ll Mempool_{ref}$, the Test Node is dropping transactions or not receiving them. This is a subtle failure mode where the node appears synced (blocks) but is useless for the network (transactions).5. Failure Mode Definitions and Detection LogicTo answer the user's core question—"At what block size does hardware become incapable?"—we must rigorously define "incapable." The software must classify node behavior into discrete states.5.1 Failure Type A: The "Slow-Death" (Linear Divergence)Mechanism: The node's verification throughput ($V_{bps}$ - Blocks Per Second) is consistently lower than the network's generation rate ($G_{bps}$).Symptom: Sync Lag increases monotonically.Detection Rule:Pythonif slope(lag_history[-10:]) > 0:
    state = "FALLING_BEHIND"
Root Cause: Usually CPU Saturation (verification math) or I/O Latency (seeking inputs).5.2 Failure Type B: The "IO Lock" (RPC Timeout)Mechanism: The monerod architecture is such that heavy I/O operations (like verifying a massive block or flushing the mempool to disk) can lock the main thread or database access threads. While the process remains "alive" (PID exists, ports open), it becomes unable to service RPC requests in a timely manner. This state is distinct from a crash; the node is "bogged down" to the point of uselessness.Symptom: The MSNM receives ReadTimeout or extreme latency (>5000ms) on get_info requests, even if the TCP connection is established. The response_time_ms metric will spike immediately preceding this state.Detection Rule:Pythontry:
    # Strict timeout is essential here to detect "bogged down" nodes
    response = rpc.get_info(timeout=5)
except Timeout:
    state = "IO_SATURATED"
Implication: This confirms the hardware's storage solution (e.g., HDD) is the bottleneck for the current block size. The node has effectively failed the stress test even if it recovers later.5.3 Failure Type C: The "Hard Crash" (Process Termination)Mechanism: The Operating System terminates monerod.OOM Killer: RAM exhaustion due to large block serialization.Segfault: Software bug triggered by stress conditions.Symptom: ConnectionRefused (TCP RST). The port is closed.Detection Rule:Pythontry:
    connect(ip, port)
except ConnectionRefused:
    state = "CRASHED"
Correlation: If this happens immediately after a block size increase, it indicates a Memory Capacity failure.5.4 Failure Type D: The "Ghost Node" (Forked/Stuck)Mechanism: The node rejects a valid large block (perhaps due to a timeout during verification or a "too big" check) and mines its own alternative chain or accepts a smaller competing chain.Symptom: Node reports status: OK, height is increasing, but cumulative_difficulty is lower than Reference, and block_hash mismatches.Detection Rule: Hash comparison logic defined in Section 4.2.6. Analytical Methodology and ReportingThe software is not just a logger; it is an analysis tool. The Coding Agent must implement logic to correlate Block Size with Node Failure and generate human-readable artifacts.7.1 The "Incapability" FunctionWe define the function $C(H, B)$ as the capability of hardware $H$ to handle block size $B$.$C(H, B) = 1$ if the node maintains $Lag < 3$ and $Reorgs < 2$ per hour.$C(H, B) = 0$ otherwise.The goal is to find $B_{max}$ where $C(H, B_{max})$ transitions from 1 to 0.7.2 Automated Reporting LogicThe MSNM must include a Reporting module capable of generating post-test artifacts. This allows for offline analysis without relying on the live dashboard.7.3 Data Export SpecificationsThe user requires the ability to export raw data for external analysis. The software must support two formats via a CLI command (e.g., python msnm.py export --format=parquet):Parquet Export (Recommended):Use Case: Large datasets, high-performance analysis in Python/Pandas/Jupyter.Schema: timestamp, node_id, block_height, lag, response_time_ms, error_state, hardware_desc.Benefit: Columnar storage allows for efficient filtering by node_id without reading the entire file.CSV Export:Use Case: Quick viewing in Excel/Sheets.Structure: Standard comma-separated values.Note: Should implement chunking if the dataset exceeds 1 million rows to prevent spreadsheet crashes.7.4 Session Summary ReportAt the conclusion of a stress test, the software must generate a Test Summary Report (Markdown or HTML). Operational Considerations and Risks8.1 Handling Reorgs and "Stuck" NodesAs noted in research on network attacks and stress, nodes can get "stuck" banning peers they deem malicious (because they sent a "too big" block that the node considers invalid). The MSNM logs must capture these events.Log Parsing: If possible, the system should ingest bitmonero.log to look for "Banned peer" messages. If a Test Node bans the Reference Node, the test is effectively broken for that node. The configuration of Test Nodes should ideally include whitelisting the Reference Node or disabling bans (--disable-rpc-ban).8.2 Checkpoints and TrustMonero uses DNS checkpoints and hardcoded checkpoints to secure the chain. In a private StressNet, these safeguards can cause nodes to reject the custom chain.Requirement: The specification requires Test Nodes to be launched with --disable-dns-checkpoints and possibly --enforce-dns-checkpointing 0 to ensure they judge the chain solely on PoW and validity, not on hardcoded expectations.8.3 Bandwidth vs. ProcessingDistinguishing between network bandwidth limits and processing limits is vital. If get_connections shows saturated bandwidth but low CPU, the failure is the network link, not the computer's processing power. The analysis logic must verify current_download rates against known link capacities.9. By building this Hub-and-Spoke telemetry system, utilizing raw JSON-RPC extraction, and implementing the rigorous failure mode definitions outlined above, the user will be able to scientifically determine the hardware requirements for larger Monero blocks. The system moves beyond anecdotal observation to provide hard data on the trade-offs between block size, hardware cost, and network decentralization, ensuring that future scaling decisions are informed by empirical evidence of hardware limits. The resulting data will allow for precise plotting of the "hardware exclusion curve"—the percentage of legacy nodes lost per megabyte of block size increase.
